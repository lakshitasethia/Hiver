# Report — Transparent AI Customer-Support Agent

_Companion to [`design.md`](design.md) (architecture),
[`decisions.md`](decisions.md) (12 non-obvious choices), and
[`real-data-notes.md`](real-data-notes.md) (the real 40k-thread Kaggle run —

**What the committed Results block is:** a real evaluation on `n=60` of the
synthetic gold-labelled set — MiniLM embeddings, generation and the zero-shot
classification baseline on Groq `openai/gpt-oss-20b`, and the LLM-judge on a
different family, Groq `qwen/qwen3.8-27b`. `n=60` rather than the full 200 only
because Groq's free tier throttles hard; the suites and the code are identical at
any `n`. `make eval` with **no** API key reproduces all three suites offline at
`n=200` with the deterministic fake (that is the CI path). Numbers between the
`<!-- BEGIN:results -->` markers are generated by `make eval`; everything else is
analysis.

## 1. Problem framing and scope

**Task.** For one inbound support message (plus up to 4 prior turns): assign an
intent, draft a brand-voice reply grounded in history, and decide `auto_send`
vs `escalate` with a reason a support lead would accept.

**Framing choice — three small transparent models, not one large opaque one.**
The assignment states "the proof is worth more than the system." An end-to-end
LLM agent would likely produce better prose, but a single failure would be
unattributable and there would be no baseline to measure against. So the system
is a pipeline of parts that can each be inspected, tested, and compared to a
naive alternative: logistic-regression classification, retrieval + few-shot
generation, and a rule engine for routing.

**Scope decisions and their costs:**

| Decision | Rationale | Cost we accept |
|---|---|---|
| One message + short history as the unit | Matches helpdesk triage; keeps eval tractable | Loses multi-turn diagnostic context |
| All ~20 brands, one shared classifier | More data per intent; brand voice handled at retrieval time | Noisier "brand voice"; thinner per-brand eval |
| English only, language-gated | Dataset is ~English; non-English is a routing target, not a feature | Non-English messages get a human, always |
| "Resolved" inferred from thread shape | No explicit resolution label exists | Counts "agent signed off politely" as success |
| Agent **drafts and routes**; a human/integration sends | Keeps the risky action (sending) outside the model | Not a fully autonomous responder |
| Intent taxonomy frozen at 10 | Enough for distinct routing, enough eval support per class | Coarser than a real helpdesk's 30–50 queues |

**Data.** Kaggle "Customer Support on Twitter" (~3M tweets, ~20 brands,
multi-turn, noisy). Threaded into conversations by `in_response_to_tweet_id`.
A credential-free synthetic corpus of the same shape
(`support_agent/data/synthetic.py`) drives CI, tests, and any run without a
Kaggle token; the code path is identical.

## 2. Approach in one paragraph

Normalise text (mask handles/URLs/PII, gate language) → embed
(`all-MiniLM-L6-v2` locally, or a deterministic hashing fallback) → classify
intent with logistic regression trained on **weak keyword labels** (hand-labels
are spent on evaluation only) → retrieve *k* similar **resolved, same-brand**
conversations → few-shot them to an LLM (Groq `gpt-oss-20b` by default) for a
draft, with a post-hoc regex check that the draft invented no specifics → extract
escalation signals
(confidence, margin, intent risk tier, sentiment, retrieval similarity, PII,
compliance keywords) → run an **ordered rule engine** that returns a decision, a
plain-English reason, and the truth value of every rule.

## 3. Baselines and how to read the comparison

| Component | Our approach | Baseline |
|---|---|---|
| Classification | logreg on embeddings | **LLM zero-shot** — the 10 intent definitions in the prompt, model returns a JSON label |
| Generation | RAG few-shot | **retrieval-only** — the single nearest resolved reply, verbatim, no LLM |
| Escalation | ordered rule engine | **confidence-threshold only**, swept across every operating point |

All three comparisons are real in the committed run (`n=60`, Groq). Offline
(`make eval`, no key) the classification/generation baselines run against the
deterministic fake and are plumbing checks, not quality — the escalation
comparison is real either way, since it uses no LLM.

### Reading the committed run (`n=60`, Groq)

- **The zero-shot LLM baseline beats our classifier — and that is the point.**
  Logreg macro-F1 **0.858** vs zero-shot `gpt-oss-20b` **0.935**: the transparent
  classifier costs about **8 macro-F1 points**. We would still ship logreg (see
  [decision #1](decisions.md)) — it is ~1 ms/message, deterministic, needs no
  key, and its coefficients are inspectable — but this is the honest price of
  that choice, and closing it (a fine-tuned encoder) is the top roadmap item.
  The two models fail differently: logreg is weak on `order_status` (recall 0.5)
  and `account_access` (recall 0.6); the LLM is weak on `product_question`
  (F1 0.73) and `account_access` (F1 0.77).
- **Calibration is the most useful classification result.** The 15 predictions
  with confidence < 0.5 are right only **47%** of the time; every bucket above
  0.5 is **100%**. Confidence cleanly separates reliable from unreliable — which
  is exactly what the `low_model_confidence` escalation rule leans on.
- **RAG generation wins the head-to-head decisively.** Blind, order-randomised
  pairwise judging by a *different* model family (Qwen judging gpt-oss output)
  prefers the RAG draft over the verbatim-retrieval baseline **32 to 3** (25
  ties). Absolute rubric scores are middling — helpfulness 2.7 / tone 3.8 /
  factual-caution 2.7, and would_send is only **0.18** — because these are
  Twitter-length drafts from noisy history and Qwen is a strict grader. So: the
  LLM clearly improves on retrieval-only, but the drafts are assist-a-human
  quality, not send-unedited quality. Groundedness is **0.97** (one draft in
  ~30 introduced an unseen specific — failure mode #3).
- **Semantic similarity favours the baseline** (0.66 vs RAG 0.60) precisely
  because it rewards copying historical phrasing; the pairwise result is the
  better signal (see §6).
- **Escalation wins regardless of the LLM.** The rule engine: weighted cost
  **12**, **zero false auto-sends**, precision 0.66 / recall 1.0. The
  confidence-only baseline at its best sweep point costs **36**; at its default
  operating point, **76** (with 14 false auto-sends — messages that should have
  gone to a human but did not). The rules catch what a single confidence number
  cannot see: compliance keywords, intent risk tier, language. The engine's cost
  is 12 needless escalations, almost all from `low_model_confidence` firing on
  low-confidence predictions — tightening the classifier shrinks this, not
  retuning the rule.
- **Offline / CI numbers differ and are lower.** `make eval` with no key runs the
  same suites at `n=200` with the fake LLM and (in CI) the hashing embedder:
  classification macro-F1 ~0.74, the fake generator is verbose and the fake judge
  ties every pair. The escalation result is essentially unchanged there — it
  barely depends on embedding or LLM quality.
- `make tune` on the dev split suggests looser thresholds that cut dev-split cost
  further; the shipped config keeps the conservative values and documents the gap
  rather than fitting the dev slice.

## 5. Five primary failure modes

**1. Low-support intents under-recall (`order_status` recall 0.5,
`account_access` 0.6 at `n=60`).**
The weak labeller tags only a thin slice of these intents' phrasings, so the
classifier never sees the long tail ("where the hell is my stuff", "it keeps
logging me out", "2FA broke"). It is worse under the hashing fallback embedder
(`order_status` recall ~0.15) and worse still on real data — see
[`real-data-notes.md`](real-data-notes.md), where weak-label coverage drops from
72% to 16%. The zero-shot LLM does not have this problem (`order_status` F1 1.0),
which is most of its 8-point macro-F1 lead.
_Example (real-data model):_ "locked out again, this is the third time this week"
→ predicted `praise_thanks` at confidence **0.19**; it still escalates via
`low_model_confidence`, but as a *misrouted* message a human must re-triage.
_Fix path:_ labelling functions for lockout/2FA phrasings, a hand-labelled seed
set per thin class, or a fine-tuned encoder ([decision #1](decisions.md)) which
needs far fewer examples per class.

**2. Sarcasm is scored as neutral or positive.**
The sentiment lexicon is bag-of-words with intensifiers; it cannot see irony.
_Example (real output):_ "Oh fantastic, another 'we're looking into it'. Love
that for me." → sentiment **+0.60**, `anger_flag=false`, so the
`angry_customer_medium_risk` rule never fires. The message still escalates if the
*intent* is high-risk or retrieval is weak, but on a medium-risk issue it can
slip through to `auto_send`. _Fix path:_ a small trained sentiment/sarcasm
classifier as one more signal, or an LLM sentiment call gated to borderline
cases.

**3. The groundedness regex over-triggers on quoted-back specifics.**
`_check_grounded` flags any order#/date/amount/time in the draft that is not a
substring of the customer message. A reply that correctly echoes "order
#48213391" when the customer wrote "order 48213391" (no `#`) fails the substring
test → `grounded=false` → the `ungrounded_draft` rule escalates a reply that was
actually fine. At `n=60` the generator's groundedness rate is **0.97** — the ~1
flagged draft in 30 is a mix of real over-trigger and the occasional genuine
invented specific. It inflates false escalations in any run that drafts before
deciding (the CLI, `make triage`); the escalation eval scores routing pre-draft
so it is not counted there. This is the safe direction to fail. _Fix path:_
normalise both sides (strip `#`, punctuation, whitespace) before the containment
check; compare extracted entities, not raw spans.

**4. Cross-brand retrieval fallback imports the wrong voice.**
When a brand has fewer than `k_min=2` resolved same-brand threads, the retriever
fills from other brands. The generator then few-shots on, say, BoltMobile's
"^JD" sign-off style for a NimbusAir customer. _Example:_ a NimbusAir draft that
ends with a terse initials sign-off instead of the "— The Nimbus Air Team ✈️"
pattern. _Fix path:_ when falling back, drop the sign-off from cross-brand
exemplars, or pass the brand's canonical sign-off explicitly and instruct the
model to use only that.

**5. The "resolved" proxy poisons the retrieval corpus with polite dead-ends.**
A thread ending in the agent's "Looking into this, back to you shortly." with no
further customer message is counted `resolved=true` and enters the corpus as a
model reply. The generator learns to stall. _Example:_ retrieval for a delivery
complaint surfaces three "we're on it, hang tight" replies and the draft says
nothing actionable. _Fix path:_ require a minimum agent-reply length and/or a
closing cue ("refunded", "shipped", "sorted") for a thread to count as resolved;
better, use a small model to score whether the last agent turn actually resolved
anything.

## 6. What the headline metrics don't capture

- **Weak-label leakage inflates CV numbers.** The classifier's cross-validated
  macro-F1 (~0.99) is measured against the same keyword rules that generated its
  labels; it mostly proves the embeddings separate the rules' decision boundary.
  Only the hand-labelled test-set macro-F1 is meaningful, and even that inherits
  any systematic gap in the labelling functions (e.g. failure mode #1).
- **LLM-judge bias — mitigated, not gone.** The committed run judges with Groq
  `qwen/qwen3.8-27b` and generates with Groq `gpt-oss-20b` — different model
  families and vendors, so "the model grades its own output" is largely avoided
  (set `SUPPORT_AGENT_JUDGE_MODEL` to change it). Still imperfect: both are
  instruction-tuned LLMs with correlated notions of a "good" reply, and Qwen's
  low `would_send` rate (0.18) may say as much about Qwen's strictness as about
  the drafts. The **pairwise** win-rate is the number to trust; the absolute 1–5
  scores are softer.
- **Semantic similarity to the historical reply rewards mimicry, not
  correctness.** The retrieval baseline scores *higher* on similarity (0.66 vs
  0.60) yet loses the blind pairwise 3–32: sounding like past replies is not the
  same as being the better reply for this customer. Treat the similarity row as
  a sanity check, not a quality score.
- **Escalation gold is itself a judgment call.** `should_escalate` is labelled
  by a policy (high-risk intent / compliance cue / anger+non-trivial /
  needs-authority). Reasonable reviewers will disagree on the borderline anger
  and product-question cases; inter-annotator noise there is unmeasured in this
  submission (the labelling guide asks for a self-diff pass as a proxy).
- **No latency or cost SLA is reported.** logreg + MiniLM is ~1 ms/message on
  CPU; the Groq generation call is ~1–5 s and, on the free tier, tokens/min
  limited (this is why the run is `n=60`). A production deployment would batch,
  cache identical retrievals, and use a cheaper judge — none of which is
  measured here.
- **Synthetic data flatters everything.** The committed numbers are on templated
  text with clean brand voices. On the real Kaggle corpus every score drops —
  weak-label coverage alone falls 72% → 16% and classifier CV macro-F1 0.99 →
  0.70 ([`real-data-notes.md`](real-data-notes.md)). Real tweets bring
  emoji-only messages, code-switching, and multiple issues per message that the
  synthetic set does not.

## 7. Future improvement roadmap

**Near term (days)**
1. Fix failure mode #3 (normalise before the groundedness containment check) —
   removes needless escalations at zero risk.
2. Add `order_status` labelling functions + a 50-example hand-labelled seed;
   re-measure per-class recall.
3. Hand-label `eval/labelset/labels.real.unlabelled.jsonl` (200 real messages,
   already seeded) and run all three suites on real data — the Groq backend is
   wired; the only blockers are the labels and free-tier throughput. Bump `n`
   toward 200 for tighter confidence intervals on the numbers above.
4. Tighten the "resolved" definition (min length + closing-cue heuristic) and
   rebuild the retrieval corpus.

**Medium term (weeks)**
5. Replace logreg with a fine-tuned `MiniLM`/`DeBERTa-small` classifier; keep
   logreg as the transparent baseline and ship whichever wins per-class.
6. Add a trained sentiment/sarcasm signal to the escalation feature set.
7. Calibrate probabilities (isotonic / temperature scaling) so confidence
   thresholds mean the same thing across intents.
8. Swap the flat NumPy retrieval for an ANN index only if corpus size demands
   it; add brand-canonical sign-off injection.

**Longer term**
9. Multi-turn context: condition classification and generation on the full
   thread, not just the first customer message.
10. Human-in-the-loop feedback: log every escalation outcome (did the human
    agree?) and every sent auto-reply's downstream signal (customer replied
    angrily? reopened?) and use it to retrain thresholds and the classifier.
11. Per-team routing beyond 10 intents once real labelled volume exists.
12. Replace the single LLM judge with a small panel (different providers) and
    report agreement, to quantify and reduce judge bias.
