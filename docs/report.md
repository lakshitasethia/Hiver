# Report — Transparent AI Customer-Support Agent

_Companion to [`design.md`](design.md) (architecture),
[`decisions.md`](decisions.md) (12 non-obvious choices), and
[`real-data-notes.md`](real-data-notes.md) (what happened on the real Kaggle
dataset — weak-label collapse, taxonomy check, real Gemini walkthrough)._

The numbers in **Results** are on the **synthetic sample corpus** (the only path
with gold labels that runs in CI with no credentials); they are regenerated by
`make eval` and never edited by hand. The real-data run is qualitative so far —
see `real-data-notes.md` for why (no hand labels yet; Gemini free tier is ~20
requests/day). Everything else here is analysis.

---

## 1. Problem framing and scope

**Task.** For one inbound support message (plus up to 4 prior turns): assign an
intent, draft a brand-voice reply grounded in history, and decide `auto_send`
vs `escalate` with a reason a support lead would accept.

**Framing choice — three small transparent models, not one large opaque one.**
The assignment states "the proof is worth more than the system." An end-to-end
LLM agent would likely produce better prose, but a single failure would be
unattributable and there would be no baseline to measure against. So the system
is a pipeline of parts that can each be inspected, tested, and compared to a
naive alternative: logistic-regression classification, retrieval + few-shot
generation, and a rule engine for routing.

**Scope decisions and their costs:**

| Decision | Rationale | Cost we accept |
|---|---|---|
| One message + short history as the unit | Matches helpdesk triage; keeps eval tractable | Loses multi-turn diagnostic context |
| All ~20 brands, one shared classifier | More data per intent; brand voice handled at retrieval time | Noisier "brand voice"; thinner per-brand eval |
| English only, language-gated | Dataset is ~English; non-English is a routing target, not a feature | Non-English messages get a human, always |
| "Resolved" inferred from thread shape | No explicit resolution label exists | Counts "agent signed off politely" as success |
| Agent **drafts and routes**; a human/integration sends | Keeps the risky action (sending) outside the model | Not a fully autonomous responder |
| Intent taxonomy frozen at 10 | Enough for distinct routing, enough eval support per class | Coarser than a real helpdesk's 30–50 queues |

**Data.** Kaggle "Customer Support on Twitter" (~3M tweets, ~20 brands,
multi-turn, noisy). Threaded into conversations by `in_response_to_tweet_id`.
A credential-free synthetic corpus of the same shape
(`support_agent/data/synthetic.py`) drives CI, tests, and any run without a
Kaggle token; the code path is identical.

## 2. Approach in one paragraph

Normalise text (mask handles/URLs/PII, gate language) → embed
(`all-MiniLM-L6-v2` locally, or a deterministic hashing fallback) → classify
intent with logistic regression trained on **weak keyword labels** (hand-labels
are spent on evaluation only) → retrieve *k* similar **resolved, same-brand**
conversations → few-shot them to Gemini Flash for a draft, with a post-hoc regex
check that the draft invented no specifics → extract escalation signals
(confidence, margin, intent risk tier, sentiment, retrieval similarity, PII,
compliance keywords) → run an **ordered rule engine** that returns a decision, a
plain-English reason, and the truth value of every rule.

## 3. Baselines and how to read the comparison

| Component | Our approach | Baseline | Fair comparison needs |
|---|---|---|---|
| Classification | logreg on embeddings | **LLM zero-shot** (taxonomy in the prompt) | `GOOGLE_API_KEY` — otherwise the baseline runs against the offline *fake* LLM and its score is a placeholder, not a real number |
| Generation | RAG few-shot | **retrieval-only** (nearest resolved reply, verbatim) | `GOOGLE_API_KEY` for the RAG side and the judge; offline, both collapse to the fake |
| Escalation | ordered rule engine | **confidence-threshold only**, swept across operating points | nothing — this comparison is valid fully offline |

So: the **escalation** result below is real regardless of setup. The
classification and generation baseline columns are only meaningful with a Gemini
key; the committed run uses the deterministic fake and labels those cells
accordingly.

### Reading the committed run

The committed run uses the **default local backends**: `all-MiniLM-L6-v2`
embeddings (a ~90 MB download, no API key) and the deterministic offline *fake*
LLM. Numbers that need Gemini are called out as placeholders. Re-running with
`SUPPORT_AGENT_EMBEDDER=hashing` (the CI config) drops classification macro-F1 to
~0.74 and the <0.5 confidence bucket to ~13% accuracy — the escalation result is
essentially unchanged, because it barely depends on embedding quality.

- **Calibration is the most useful classification result.** Overall macro-F1 is
  **0.86**, but the 55 predictions with confidence < 0.5 are right only **53%**
  of the time, while every bucket above 0.5 is ~100%. Confidence genuinely
  separates reliable from unreliable predictions — which is what the
  `low_model_confidence` escalation rule depends on.
- **`account_access` recall (0.45) is the standout weakness** — only 26
  weakly-labelled training rows and its phrasings ("can't get in", "2FA broke",
  "keeps signing me out") vary more than the keyword rules cover. It is
  high-risk, so misroutes still escalate on intent-risk grounds, but they escalate
  as the *wrong* intent. `praise_thanks` precision (0.67) is the opposite error:
  polite phrasing in complaints ("thanks for nothing") leaks in.
- **The classification baseline column is a placeholder.** 0.018 is the offline
  fake LLM, not Gemini zero-shot. With `GOOGLE_API_KEY` this becomes a real
  comparison; expect Gemini zero-shot to land in the 0.6–0.8 macro-F1 range and
  the interesting question to be latency/cost/determinism, not just F1.
- **Escalation wins decisively and API-key-free.** The rule engine reaches a
  weighted cost of **43** with **zero false auto-sends**; the best the
  confidence-only baseline manages at any threshold is **124**, and its default
  operating point is **245** (missing 44 escalations). The rules convert signals
  the single confidence number cannot see — compliance keywords, intent risk,
  language — into catches. Its cost is 43 needless escalations (precision 0.63),
  almost all from the `low_model_confidence` rule firing on the 55 sub-0.5
  predictions; tightening the classifier (failure mode #1) is what shrinks this,
  not tuning the rule.
- **Generation numbers are plumbing checks, not quality.** The fake LLM is
  verbose (length ratio 2.4) and the fake judge ties every pairwise comparison.
  Run with `GOOGLE_API_KEY` for real generation/judge figures; the harness,
  rubric, randomised pairwise, and groundedness check all run as-is.
- `make tune` on the dev split suggests looser thresholds (conf 0.45 / margin
  0.05 / sim 0.35) that cut dev-split cost sharply; the shipped config keeps the
  conservative values and documents the gap rather than fitting the dev slice.

## 5. Five primary failure modes

**1. Low-support intents under-recall (worst: `account_access`, recall 0.45).**
The weak labeller tagged only 26 `account_access` and 17 `order_status` training
rows, so the classifier never saw the long tail of phrasings ("can't get in",
"it keeps logging me out", "2FA broke"). Under the hashing fallback embedder
`order_status` recall collapses to 0.15; with `all-MiniLM` it recovers to 0.75
but `account_access` stays weak.
_Example (real output):_ "locked out again, this is the third time this week" →
predicted `praise_thanks` at confidence **0.19** (it escalates anyway, via
`low_model_confidence` — but as a misclassified message a human now has to
re-triage). _Fix path:_ add labelling functions for lockout/2FA phrasings,
hand-label a small seed set per thin class, or move to a fine-tuned encoder
(decision #1) which needs far fewer examples per class.

**2. Sarcasm is scored as neutral or positive.**
The sentiment lexicon is bag-of-words with intensifiers; it cannot see irony.
_Example (real output):_ "Oh fantastic, another 'we're looking into it'. Love
that for me." → sentiment **+0.60**, `anger_flag=false`, so the
`angry_customer_medium_risk` rule never fires. The message still escalates if the
*intent* is high-risk or retrieval is weak, but on a medium-risk issue it can
slip through to `auto_send`. _Fix path:_ a small trained sentiment/sarcasm
classifier as one more signal, or an LLM sentiment call gated to borderline
cases.

**3. The groundedness regex over-triggers on quoted-back specifics.**
`_check_grounded` flags any order#/date/amount/time in the draft that is not a
substring of the customer message. A reply that correctly echoes "order
#48213391" when the customer wrote "order 48213391" (no `#`) fails the substring
test → `grounded=false` → the `ungrounded_draft` rule escalates a reply that was
actually fine. It shows up as the gap between the generator's groundedness rate
(0.88) and a true hallucination rate, and it will inflate false escalations in
any run that drafts a reply before deciding (the CLI and `make triage`; the
escalation eval scores routing pre-draft so it is not counted there). This is the
safe direction to fail. _Fix path:_ normalise both sides (strip `#`, punctuation,
whitespace) before the containment check; compare extracted entities, not raw
spans.

**4. Cross-brand retrieval fallback imports the wrong voice.**
When a brand has fewer than `k_min=2` resolved same-brand threads, the retriever
fills from other brands. The generator then few-shots on, say, BoltMobile's
"^JD" sign-off style for a NimbusAir customer. _Example:_ a NimbusAir draft that
ends with a terse initials sign-off instead of the "— The Nimbus Air Team ✈️"
pattern. _Fix path:_ when falling back, drop the sign-off from cross-brand
exemplars, or pass the brand's canonical sign-off explicitly and instruct the
model to use only that.

**5. The "resolved" proxy poisons the retrieval corpus with polite dead-ends.**
A thread ending in the agent's "Looking into this, back to you shortly." with no
further customer message is counted `resolved=true` and enters the corpus as a
model reply. The generator learns to stall. _Example:_ retrieval for a delivery
complaint surfaces three "we're on it, hang tight" replies and the draft says
nothing actionable. _Fix path:_ require a minimum agent-reply length and/or a
closing cue ("refunded", "shipped", "sorted") for a thread to count as resolved;
better, use a small model to score whether the last agent turn actually resolved
anything.

## 6. What the headline metrics don't capture

- **Weak-label leakage inflates CV numbers.** The classifier's cross-validated
  macro-F1 (~0.99) is measured against the same keyword rules that generated its
  labels; it mostly proves the embeddings separate the rules' decision boundary.
  Only the hand-labelled test-set macro-F1 is meaningful, and even that inherits
  any systematic gap in the labelling functions (e.g. failure mode #1).
- **The LLM judge shares a family with the generator.** Gemini judging Gemini
  drafts will favour their shared style. Mitigations in place: fixed rubric,
  temperature 0, position-randomised pairwise, and human spot-checks — but the
  bias is not removed. Pairwise win-rate vs the retrieval baseline is more
  trustworthy than the absolute 1–5 scores.
- **Semantic similarity to the historical reply rewards mimicry, not
  correctness.** A draft can score high by sounding like past replies while
  being wrong for this customer; a genuinely better reply that departs from
  house style is penalised.
- **Escalation gold is itself a judgment call.** `should_escalate` is labelled
  by a policy (high-risk intent / compliance cue / anger+non-trivial /
  needs-authority). Reasonable reviewers will disagree on the borderline anger
  and product-question cases; inter-annotator noise there is unmeasured in this
  submission (the labelling guide asks for a self-diff pass as a proxy).
- **No latency or cost budget is reported.** logreg + hashing is ~1 ms/message;
  the Gemini generation call is ~1–2 s and rate-limited on the free tier. A
  production SLA would change the design (batch, cache, cheaper judge).
- **Synthetic data flatters everything.** The committed numbers are on templated
  text with clean brand voices. Real tweets are messier — emoji-only messages,
  code-switching, multiple issues per message — and every score should be
  expected to drop on the real corpus.

## 7. Future improvement roadmap

**Near term (days)**
1. Fix failure mode #3 (normalise before the groundedness containment check) —
   removes needless escalations at zero risk.
2. Add `order_status` labelling functions + a 50-example hand-labelled seed;
   re-measure per-class recall.
3. Run the full pipeline on the real Kaggle data with `GOOGLE_API_KEY` and
   publish the real classification/generation/judge numbers alongside these.
4. Tighten the "resolved" definition (min length + closing-cue heuristic) and
   rebuild the retrieval corpus.

**Medium term (weeks)**
5. Replace logreg with a fine-tuned `MiniLM`/`DeBERTa-small` classifier; keep
   logreg as the transparent baseline and ship whichever wins per-class.
6. Add a trained sentiment/sarcasm signal to the escalation feature set.
7. Calibrate probabilities (isotonic / temperature scaling) so confidence
   thresholds mean the same thing across intents.
8. Swap the flat NumPy retrieval for an ANN index only if corpus size demands
   it; add brand-canonical sign-off injection.

**Longer term**
9. Multi-turn context: condition classification and generation on the full
   thread, not just the first customer message.
10. Human-in-the-loop feedback: log every escalation outcome (did the human
    agree?) and every sent auto-reply's downstream signal (customer replied
    angrily? reopened?) and use it to retrain thresholds and the classifier.
11. Per-team routing beyond 10 intents once real labelled volume exists.
12. Replace the single LLM judge with a small panel (different providers) and
    report agreement, to quantify and reduce judge bias.
